# Godot 4 draws your translation with a font it borrowed from the player's PC

**35 claims, every one of them printed by `docs/verify_font_glyphs.sh` against
Godot 4.7.stable.official.5b4e0cb0f.** Re-run it after a Godot upgrade; the
coverage table below is generated by that script, not typed by hand.

There is a class of bug reports that every "my translation is not working"
checklist gets wrong, this repo's own included:

> *"Chinese looks perfect on my machine. Two players say the menu is a row of
> little boxes."*

Nothing is wrong with the translation. `tr("MENU_START")` returns `开始`
correctly (`T1`, `T2`). The table is loaded, the locale is right, the key
matches. What is missing is a *glyph*, and Godot went and found one on your
computer — a file that is not in your export.

## What the engine actually guarantees

Godot's built-in UI font is **Open Sans SemiBold**, and it is a subset. Asking
the engine `ThemeDB.fallback_font.has_char(cp)` for every codepoint in the BMP,
the emoji planes and CJK Extension B gives an exact answer:

**1010 codepoints, in 92 ranges** (`G1`, `Y1`).

| script | in the built-in font? | claim |
|---|---|---|
| printable ASCII `0x20`–`0x7E` | yes, all of it | `G2` |
| Latin-1 accents — `é ã ç` (fr/pt/es) | yes | `G3` |
| Latin Extended-A — `ł š ğ` (pl/cs/tr) | yes | `G4` |
| Vietnamese — `ạ` (U+1EA1) | yes | `G5` |
| Cyrillic — `Ж` | yes | `G6` |
| Greek — `α` | yes | `G7` |
| Hebrew — `א` | yes | `G8` |
| Arabic — `ب` | **no** | `G9` |
| Chinese — `你`, `我` | **no** | `G10` |
| Japanese kana — `あ`, `ア` | **no** | `G11` |
| Korean — `가` | **no** | `G12` |
| Thai — `ก` | **no** | `G13` |
| Devanagari — `क` | **no** | `G14` |
| emoji — `😀` | **no** | `G15` |
| arrows — `← ↑ → ↓` | **no** | `G16` |

| `✓` `★` `♥` `♪` | **no** | `G18` |

Two rows there are worth stopping on.

`G16`/`G18`: **this is not a "non-Latin languages" problem.** A project with no
translation at all, whose entire UI is English, ships a hex box the moment a
designer writes `Continue → Next` or `OK ✓`. The em dash, the ellipsis, the
curly quotes and the euro sign *are* in the font (`G17`), so "it's not ASCII" is
not the rule and guessing does not work — which is exactly why the coverage
table is measured instead of assumed.

## Then why does it look fine here?

Because Godot borrows. Shaping `你好` with the built-in font still yields two
real glyphs (`S1`), and they carry a `font_rid` that is **not** the built-in
font's (`S2`). `OS.get_system_font_path_for_text("Sans", "你好")` names the file
it went to — on the machine that produced this document:

```
["/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc",
 "/usr/share/fonts/opentype/unifont/unifont.otf"]
```

An absolute OS path, not a `res://` path (`S3`). Same story for an emoji in a
UI string (`Y2`). None of that travels inside your `.pck`. Your development
machine — a full desktop OS with a font package installed — is the single worst
place to test whether your player can read your game.

## What the player without that font sees

`FontFile.allow_system_fallback = false` reproduces it, and it is the closest
thing to a "player's machine" you can run in CI:

- the same two-character string becomes **2 undrawable glyphs** (`S4`), while an
  ASCII string is untouched (`S5`);
- one arrow inside an otherwise ASCII line is 1 undrawable glyph (`S6`);
- the correct, properly translated `开始` from `tr()` is 2 undrawable glyphs
  (`T3`). The data is right and the pixels are not.

### The marker is not glyph index 0

If you go looking for this in code, do not test for a zero glyph index — you
will find nothing. Godot marks an undrawable codepoint by putting **the
codepoint itself** in `index` and leaving `font_rid` **invalid** (`S4b`):

```
你好 | index=20320 (U+4F60)  font_rid=RID(0)  valid=false
```

That pair is the hex box on screen. It is also the only reliable way to detect
this from inside the running game.

## Why nothing warns you

- `get_string_size()` returns a **non-zero width** for text the font cannot
  draw (`S8`), so layout does not collapse and no assert upstream trips.
- Nothing is printed to the console.
- `has_char()` says `false` for `U+4F60` *while shaping is drawing it* from a
  borrowed font (`S7`). The project-side check and the screen disagree, and both
  are telling the truth about different things.
- `tr()` returns the translated string, not the key (`T2`) — so every
  "Godot prints the raw key" checklist, including
  [ours](missing-translations-checklist.md), sends you looking in the wrong
  place.

## The fix, and the shape of it

Bundle a font that owns the codepoints you ship, and put it in `fallbacks`:

```gdscript
var body := FontFile.new()
body.load_dynamic_font("res://fonts/NotoSansSC-Regular.ttf")

var ui := ThemeDB.fallback_font.duplicate()
ui.allow_system_fallback = false   # fail loudly here, not on a player's PC
ui.fallbacks = [body]
```

Measured: with system fallback off, a `Font` in `fallbacks` takes the arrow's
undrawable glyph to zero (`S10`). Measured just as carefully: the *same*
fallback does **not** fix Chinese, because DejaVu Sans has no CJK either
(`S11`). A fallback only covers what it actually owns, so "add a fallback font"
is not advice until you know which codepoints you are actually shipping.

Which is the one question a tool can answer for you.

## Finding out what you ship

`docs/scan_translation_glyphs.js` reads your translation CSVs and lists, per
locale column, every character outside those 1010 codepoints — with the block
it belongs to and the key it appears in:

```
$ node docs/scan_translation_glyphs.js path/to/project
engine 4.7-stable (official) — built-in font Open Sans SemiBold draws 1010 codepoints

  [en] 1 characters the built-in font cannot draw — Arrows
      U+2192  "→"       Arrows ×1  in HUD_NEXT
      → NOT in the built-in font, even though the text around it is ASCII
  [zh] 9 characters the built-in font cannot draw — Arrows, CJK Unified Ideographs
      ...
      → bundle a Chinese/Japanese font
```

Exit 0 when everything is inside the built-in font, 1 when it is not, `--json`
for CI. Zero dependencies, reads only `.csv`, writes nothing.

The matching and the coverage table live in `docs/glyph-scan-core.js`, with no
filesystem in it, so the identical bytes also run in a browser for people
without a terminal:
<https://blobsmith.lbwma.com/godot-missing-characters-in-translation/>

## What this is not

This is deliberately **not** a LocGuard rule. Every rule in the linter answers
"is this translation table complete and consistent" and is fixed by editing the
table. This one answers "can the engine draw it", and the fix is a font file —
a different question, a different artifact, and a check that would be wrong to
fail a translator's build over.

**LocGuard Pro** — the editor dock and CLI that catch the table-side failures
(missing keys, empty translations, placeholder drift, unbalanced BBCode) before
your players do: <https://blobsmith.itch.io/locguard>. The free CLI is
[locguard-lite](https://github.com/leobaray/locguard-lite).
